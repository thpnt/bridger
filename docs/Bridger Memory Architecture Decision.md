# Bridger Architecture Decision — Agentic Codebase Memory Layer

## Status

Accepted for Bridger v0 / hackathon scope.

This document captures the architecture decision for Bridger’s agentic codebase memory layer, based on the agreed product direction:

> Bridger applies the LLM Wiki / compiled memory paradigm to codebases, but with a deterministic codebase compiler and multiple specialized memory agents.

---

## 1. Context

Bridger is a cross-platform context compiler and instruction generator for AI coding agents.

Its goal is not to become another coding agent. Its goal is to compile repository knowledge into a durable, reviewable, agent-ready memory layer that can be consumed by tools such as Codex, Claude Code, Cursor, Copilot, and future AI coding agents.

The core idea is inspired by the LLM Wiki / compiled memory paradigm:

```txt
raw sources
→ compiled memory
→ agent-facing instructions and prompts
```

For Bridger, this becomes:

```txt
codebase
→ .bridger memory layer
→ AGENTS.md / CLAUDE.md / Cursor rules / task-specific prompts
```

The key difference is that Bridger does not rely on one general-purpose LLM maintaining the whole memory. Instead, it uses:

1. a deterministic codebase indexer/parser/compiler;
2. structured repo intelligence artifacts;
3. multiple specialized memory agents;
4. a central orchestrator;
5. agent-facing exports and task-specific prompt generation.

---

## 2. Core architecture decision

Bridger will use:

```txt
Centralized deterministic orchestration
+ deterministic codebase compiler
+ specialized memory agents as bounded transformations
+ final export / reconciliation step
```

Bridger will not use fully autonomous multi-agent collaboration for v0.

The system should be designed around this principle:

```txt
The deterministic compiler selects and structures evidence.
Specialized LLM agents interpret curated evidence.
The orchestrator owns execution, validation, writing, and exports.
```

This means LLM agents should not freely explore the repository from scratch. They should receive curated, role-specific context generated by the deterministic compiler.

---

## 3. Why this decision

### Problems with an LLM-only approach

An LLM-only approach would ask agents to explore the repository, decide what matters, and write memory files directly.

This creates risks:

- agents may inspect the wrong files;
- agents may overfit to whichever files they saw first;
- different agents may duplicate work;
- memory may become inconsistent;
- outputs are harder to debug;
- token usage becomes less predictable;
- traceability becomes weaker;
- the system becomes too non-deterministic for a developer tool.

### Benefits of the chosen architecture

The chosen architecture is:

- more deterministic;
- easier to test;
- easier to debug;
- cheaper to run;
- easier to explain;
- easier to evaluate later;
- better aligned with local-first developer tooling;
- better suited to reviewable repository memory.

Bridger’s value should come from better compiled context, not from agents chatting with each other.

---

## 4. High-level architecture

```txt
Repository files
  ↓
Codebase Intelligence Compiler
  ↓
RepoGraph + CodebaseMap + ReadingPlans
  ↓
Memory Orchestrator
  ↓
Specialized Memory Agents
  ↓
.bridger memory files
  ↓
Agent-specific exports + task-specific prompt generator
```

---

## 5. Main components

## 5.1 Codebase Intelligence Compiler

The Codebase Intelligence Compiler is the deterministic foundation of Bridger.

It is responsible for extracting structural facts from the repository without LLM calls.

Responsibilities:

- scan repository files;
- detect languages;
- detect stack/framework signals;
- parse imports;
- build the repository graph;
- classify file roles;
- detect entrypoints;
- detect tests, fixtures, configs, docs, scripts, routes, models, schemas, services, and utilities;
- detect external library/framework signals;
- compute fan-in/fan-out;
- build subsystem clusters;
- produce deterministic graph and map artifacts.

Outputs:

```txt
.bridger/artifacts/repo-graph.json
.bridger/artifacts/codebase-map.json
.bridger/artifacts/graph-summary.json
```

This layer should be:

- deterministic;
- API-key-free;
- testable;
- reasonably fast;
- conservative in its claims.

It is the equivalent of a compiler frontend.

```txt
repo files → structural facts
```

---

## 5.2 Reading Plan Builder

The Reading Plan Builder converts structural codebase intelligence into role-specific context plans.

It answers:

```txt
Which files should each memory agent read?
In which order?
Grouped into which batches?
For what reason?
With what role in the batch?
```

The output should not be a single flat “important files” list.

It should produce structured reading batches, for example:

```txt
ArchitectureAgent:
  - project orientation
  - entrypoints
  - subsystem clusters
  - shared contracts
  - remaining source files

TestingAgent:
  - test setup
  - representative tests
  - fixtures
  - source files under test
  - remaining tests

ConventionsAgent:
  - representative source files
  - models / schemas
  - services / utilities
  - tests
  - config files

SecurityAgent, later:
  - auth/session boundaries
  - API routes
  - validation schemas
  - env/config handling
  - external integrations
```

Outputs:

```txt
.bridger/artifacts/reading-plans.json
```

The Reading Plan Builder is the bridge between raw repository structure and useful agent memory.

---

## 5.3 Memory Orchestrator

The Memory Orchestrator owns the multi-agent execution.

It is not itself a reasoning agent. It is a deterministic controller.

Responsibilities:

- load the agent registry;
- load repo graph, codebase map, and reading plans;
- build a memory run plan;
- assemble context for each specialist agent;
- decide which agents run;
- decide execution order;
- run agents in parallel where possible;
- validate outputs;
- write `.bridger` memory files;
- optionally run a final consistency/reconciliation pass;
- trigger agent-specific exports.

The orchestrator owns the run. Agents do not own the run.

For v0, the orchestrator should run specialized agents as bounded transformations:

```txt
agent input package
→ specialist LLM call
→ constrained output
→ validation
→ memory file write
```

---

## 5.4 Specialized Memory Agents

Specialized memory agents are responsible for maintaining specific memory domains.

Initial v0 agents:

```txt
RepoAnalysisAgent
ArchitectureAgent
BusinessLogicAgent
ConventionsAgent
TestingAgent
```

Possible v1 agents:

```txt
SecurityAgent
PerformanceAgent
APIContractAgent
DatabaseAgent
FrontendAgent
BackendAgent
MigrationAgent
```

Each agent should have:

- an ID;
- a target memory file;
- a purpose;
- expected input reading plan;
- expected output sections;
- grounding rules;
- unknowns policy;
- output rules;
- update rules.

Example conceptual definition:

```ts
type MemoryAgentDefinition = {
  id: "architecture";
  targetFile: ".bridger/memory/architecture.md";
  purpose: "Explain system structure, entrypoints, subsystems, and dependency flow.";
  readingPlanKind: "architecture";
  outputSections: string[];
  groundingPolicy: "use-provided-context-only";
};
```

Agents should not receive the whole repository. They should receive:

- their role instructions;
- the current memory file, if running in update mode;
- their doc-specific reading plan;
- relevant file contents;
- relevant graph/codebase metadata;
- output rules;
- unknowns policy.

## 5.5 `.bridger` Memory Store

The `.bridger` directory is the canonical compiled memory layer.

Recommended v0 structure:

```txt
.bridger/
  index.md
  log.md

  memory/
    repo-analysis.md
    architecture.md
    business-logic.md
    conventions.md
    testing.md

  artifacts/
    repo-graph.json
    graph-summary.json
    codebase-map.json
    reading-plans.json

  exports/
    AGENTS.generated.md
    CLAUDE.generated.md
```

Important distinction:

```txt
.bridger/memory = canonical compiled memory
AGENTS.md / CLAUDE.md / Cursor rules = derived exports
```

The root-level agent instruction files are generated from `.bridger` memory. They should not be treated as the canonical internal representation.

---

## 5.6 Agent-Specific Export Layer

The export layer converts `.bridger` memory into formats usable by coding agents.

Possible outputs:

```txt
AGENTS.md
CLAUDE.md
.cursor/rules/bridger.mdc
.github/copilot-instructions.md
```

The export layer should be downstream of `.bridger/memory`.

The long-term principle is:

```txt
One codebase.
One shared compiled memory layer.
Many agent-specific interfaces.
```

---

## 5.7 Ticket / Prompt Generator

The ticket or prompt generator is the second major product loop.

Its goal is to turn a rough task into an implementation-ready prompt for a coding agent.

Input:

- user task;
- compiled `.bridger` memory;
- codebase map;
- reading plans;
- relevant source files or file summaries;
- optionally current git diff in future versions.

Output:

- a project-aware implementation prompt;
- relevant files to inspect;
- implementation constraints;
- architecture notes;
- coding conventions;
- testing expectations;
- acceptance criteria;
- risk areas.

V0 flow:

```txt
bridger prompt "Add feature X"
  ↓
classify task type
  ↓
select relevant memory files
  ↓
select relevant clusters/files from CodebaseMap
  ↓
render implementation prompt
```

Possible internal structure:

```ts
type PromptGenerationPlan = {
  taskType:
    | "feature"
    | "bugfix"
    | "refactor"
    | "test"
    | "docs"
    | "security"
    | "unknown";

  relevantMemoryFiles: string[];
  relevantClusters: string[];
  candidateFiles: string[];
  riskAreas: string[];
  testingExpectations: string[];
};
```

For v0, the prompt generator can use the memory produced during `bridger init`. It does not need to run all specialist memory agents again.

## 6. v0 `bridger init` execution flow

The v0 `init` flow should generate the initial codebase memory.

```txt
bridger init
  ↓
scanRepository()
  ↓
buildRepoGraph()
  ↓
buildCodebaseMap()
  ↓
buildReadingPlans()
  ↓
buildMemoryRunPlan()
  ↓
runMemoryAgents()
  ↓
writeMemoryFiles()
```

Recommended agent dependency flow:

```txt
RepoGraph / CodebaseMap / ReadingPlans
  ↓
parallel memory agents:
  - RepoAnalysisAgent
  - ArchitectureAgent
  - BusinessLogicAgent
  - ConventionsAgent
  - TestingAgent
```

The agents can run mostly in parallel because each agent owns a separate target file.

---

## 7. v1 `bridger update` execution flow

`bridger update` is not required for the hackathon v0, but the architecture should prepare for it.

The v1 update flow should be incremental.

```txt
changed files / git diff
  ↓
rebuild affected graph/map parts or full deterministic artifacts
  ↓
identify affected clusters
  ↓
identify affected memory files
  ↓
run only relevant specialist agents in update mode
  ↓
propose memory diffs
  ↓
developer reviews
  ↓
regenerate exports
```

Update mode is different from init mode.

```txt
init mode:
  create complete memory file

update mode:
  read current memory
  read changed files and affected context
  propose minimal patch
```

The update flow should eventually support:

- changed-file detection;
- affected-cluster detection;
- affected-memory mapping;
- stale claim detection;
- reviewable patches;
- export regeneration.

## 8. Agent input contract

Every memory agent should receive a structured input package.

Conceptual shape:

```ts
type MemoryAgentInput = {
  repoMetadata: {
    rootName: string;
    detectedStack: string[];
    packageManager?: string;
  };

  targetDoc: {
    path: string;
    currentContent?: string;
    expectedSections: string[];
  };

  codebaseMap: CodebaseMapSummary;

  readingPlan: ReadingPlan;

  readingBatches: Array<{
    id: string;
    title: string;
    purpose: string;
    files: Array<{
      path: string;
      reason: string;
      roleInBatch: string;
      content: string;
    }>;
  }>;

  instructions: {
    groundingRules: string[];
    outputRules: string[];
    unknownsPolicy: string;
  };
};
```

This avoids vague prompts such as:

```txt
Here is the repo. Write architecture.md.
```

Instead, agents receive scoped instructions such as:

```txt
You are the ArchitectureAgent.
Your target file is .bridger/memory/architecture.md.
Use only these reading batches.
Explain architecture, entrypoints, subsystem responsibilities, and dependency flow.
Do not invent business behavior.
List unknowns separately.
```

---

## 9. Agent output contract

For v0, markdown output is acceptable, but it should be constrained.

Minimum output expectations:

- valid markdown;
- required sections;
- explicit `Unknowns` section;
- no unsupported claims;
- no generic filler;
- practical guidance for coding agents.

Possible structured output shape later:

```ts
type MemoryAgentOutput = {
  targetFile: string;
  markdown: string;
  diagnostics: {
    weakClaims: string[];
    missingContext: string[];
    suggestedFollowUpFiles: string[];
  };
};
```

Recommended v0 compromise:

```txt
Markdown output
+ required sections
+ explicit Unknowns section
+ optional Diagnostics section
```

For v1, structured output and diagnostics should become more important.

## 10. Hackathon v0 scope

For the hackathon demo, the goal is to prove that Bridger improves coding-agent performance by compiling useful project context.

Minimum v0 components:

```txt
1. Repo scanner / parser
2. RepoGraph
3. CodebaseMap
4. ReadingPlans
5. MemoryAgentRegistry
6. MemoryOrchestrator
7. 5–6 specialist memory agents
8. .bridger memory writer
9. AGENTS.md exporter
10. bridger prompt generator
```

Out of scope for hackathon v0:

```txt
incremental update
full traceability system
claim-level provenance
formal eval suite
security specialist
MCP server
hosted dashboard
agent-to-agent chat
reviewable patch UI
advanced linting
multi-user governance
```

The hackathon demo should show:

```txt
Before:
  coding agent receives a rough task and lacks project context.

After:
  bridger init creates .bridger memory.
  bridger prompt creates a better implementation brief.
  coding agent produces more aligned work with fewer assumptions.
```

## 12. Evaluation and traceability

Evaluation and traceability are important, but not part of the hackathon v0 scope.

They should be addressed in v1.

Future traceability should capture:

- which files each agent saw;
- which reading plan was used;
- which model was used;
- which memory file was updated;
- which claims changed;
- which source files support major claims;
- which exports were regenerated.

Future evaluation should compare coding-agent performance:

```txt
without Bridger context
vs
with Bridger-generated context
vs
with Bridger task-specific prompt
```

Potential metrics:

- correct files touched;
- fewer hallucinated files/APIs;
- better adherence to conventions;
- better tests;
- fewer failed checks;
- fewer clarification loops;
- lower human steering effort.

These are not required for v0, but the architecture should keep them possible.

---

## 13. Explicit non-goals

For the current phase, Bridger should not try to become:

- a coding agent;
- an autonomous PR bot;
- an IDE replacement;
- a vector database product;
- a SaaS dashboard-first product;
- a fully autonomous multi-agent society;
- a generic documentation generator;
- a black-box memory system.

Bridger should remain:

```txt
a local-first codebase context compiler
and instruction generator for AI coding agents
```

---

## 14. Final decision summary

Bridger will implement an agentic codebase memory layer using:

```txt
deterministic repo intelligence
+ role-specific reading plans
+ centrally orchestrated specialist memory agents
+ reviewable .bridger memory
+ agent-specific exports
+ task-specific prompt generation
```

The v0 system should prioritize correctness, simplicity, determinism, and demoability.

The chosen architecture is:

```txt
Repository
  ↓
Deterministic compiler
  ↓
RepoGraph / CodebaseMap / ReadingPlans
  ↓
Memory Orchestrator
  ↓
Specialized memory agents
  ↓
.bridger memory
  ↓
AGENTS.md / CLAUDE.md / task prompts
```

This keeps Bridger aligned with its product thesis:

> Coding agents perform better when they use compiled, reviewable, project-specific memory grounded in the actual codebase.
